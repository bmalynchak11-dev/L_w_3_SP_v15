# Відповіді на запитання

---

### 1. Системні виклики Linux та відповідні Python API

У рішенні задачі 5 використано наступні зіставлення системних викликів та інтерфейсів Linux:
- `unshare(2)` з прапорцями `CLONE_NEWUSER`, `CLONE_NEWPID`, `CLONE_NEWNS` $\rightarrow$ `os.unshare()`.
- `fork(2)` $\rightarrow$ `os.fork()`.
- `mount(2)` $\rightarrow$ виклик `libc.mount()` через `ctypes.CDLL(None, use_errno=True)` для виконання `MS_REC | MS_PRIVATE` та монтування приватного `proc` на `/proc`.
- `pipe(2)` $\rightarrow$ `os.pipe()` для каналу передачі стану (JSON) та синхронізації процесів.
- `write(2)` та `read(2)` $\rightarrow$ `os.write()`, `os.read()`, а також стандартний файловий запис при налаштуванні `/proc/self/setgroups`, `/proc/self/uid_map`, `/proc/self/gid_map`.
- `waitpid(2)` $\rightarrow$ `os.waitpid()` для очікування завершення нащадків та перевірки їхнього коду повернення через макроси WIFEXITED / WEXITSTATUS.
- `kill(2)` $\rightarrow$ `os.kill(pid, 0)` для зондування існування процесу без відправки реального руйнівного сигналу.
- `getpid(2)` та `getppid(2)` $\rightarrow$ `os.getpid()`, `os.getppid()`.

### 2. Помилки та запобіжні заходи

Під час проєктування та реалізації було враховано наступні критичні механізми:
1. **Відкладена дія `CLONE_NEWPID`:** Системний виклик `unshare(CLONE_NEWPID)` не змінює простір імен поточного процесу — він призначає новий простір лише для його майбутніх нащадків. Якщо не викликати `fork()`, PID залишиться старим значенням хоста. Тому після конфігурації обов'язково викликається `os.fork()`, і вже нащадок стає процесом `init` (PID 1).
2. **Запобігання "зомбі-процесам" та подвійному поверненню:** Дочірні процеси завжди завершуються системним викликом `os._exit()`, а не `sys.exit()`. Це запобігає повторному очищенню буферів та поверненню виконання у батьківський код або тестовий фреймворк. Перед будь-яким fork скидаються буфери через `sys.stdout.flush()` та `sys.stderr.flush()`.
3. **Запобігання витоку інформації хоста через `/proc`:** Якщо просто змонтувати `/proc`, зміни можуть поширитися на весь хост, або у новому просторі залишаться старі процеси. Для запобігання цьому обов'язково створюється `CLONE_NEWNS`, кореневий каталог робиться приватним (`MS_REC | MS_PRIVATE`), і лише після цього здійснюється монтування `proc` на `/proc`.
4. **Зависання каналів (deadlocks):** Обидва кінці кожного `pipe` коректно закриваються: невикористовувані кінці закриваються одразу після `fork()`, а кінець запису закривається перед читанням або виходом, щоб процес, який читає, отримав коректний `EOF`.

### 3. Межі ізоляції міні-контейнера та безпека

Ця частина міні-контейнера ізолює виключно таблицю процесів (нумерацію та видимість процесів через `/proc`). Проте таке середовище **не є повноцінною безпечною пісочницею** через наступні причини:
- **Спільне ядро Linux:** Контейнер використовує те саме ядро хоста. Будь-яка вразливість нульового дня (0-day) або race-condition у ядрі дозволяє вийти за межі ізоляції.
- **Відсутність Seccomp:** Без фільтрації системних викликів (`seccomp-bpf`) процес усередині контейнера може виконувати потенційно небезпечні або застарілі виклики (наприклад, роботу з ключами ядра, `ptrace`, створення сирих сокетів тощо).
- **Мережевий стек:** Без простору `CLONE_NEWNET` процес розділяє мережеві інтерфейси хоста, може слухати локальні порти та перехоплювати трафік.
- **Файлова система:** Без безпечного `chroot` / `pivot_root` змонтовані системні шляхи залишаються доступними.
- **Обмеження ресурсів:** Без `cgroups v2` та `rlimit` процес може виконати форк-бомбу або заповнити всю оперативну пам'ять машини (Out-Of-Memory), що призведе до Denial of Service для всього хоста.
